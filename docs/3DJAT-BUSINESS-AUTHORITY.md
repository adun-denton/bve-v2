# Offline business context authority — J07-C2-P1-BA1 candidate

This file-owned module adds one approved business context publication and an exact selected-head read. It is not connected to Kernel, HTTP, SQLite, an operating native host or an installed workspace. The `business-context.v1` record remains unchanged. A new `business-decision.v1` record, a signed evidence record and the context revision are published in one Store receipt. The decision ID equals the event/evidence ID; the decision points at the exact action event ref and the context points at the exact decision and evidence refs. The verifier reconstructs the complete signed command and canonical receipt plan across the selected ancestry. Store closure and head pointer alone never establish approval.

The local `DomainBusiness(root,{accessFile,authenticate,hook})` requires a native callback with descriptor-safe `{id,role,products}` or `{id,role,products,sourceIds}`. The optional native source IDs are ignored. Business access requires native `products:'*'`, exact private workspace/identity/role and a separate business grant. A registered human with `read` can select; publishing needs human `read` and `publish`; a registered conductor may read. No bearer fallback, product grant, template grant, caller boolean, user-supplied key or command path grants business authority. The callback and private policy are checked again at the relevant read, lock, publication, replay and return fences. A changed retained key refuses verification; no key rotation history is invented.

`business.context.publish` accepts a closed command.v1 packet with workspace ID, expected business revision, next revision, instructions, 1–16 ordered source refs, exact UTC decision time and the derived human action ref. It approves the complete content in one native human action. Replacements create immutable later revisions. Same-key exact replay proves the original publication under current grants without reopening source bytes. Changed payload conflicts. A commit uncertainty is reported for owner reconciliation, with no automatic retry or lock cleanup. A signed action does not prove actual external operational event delivery or a real-world person's legal identity.

`resolveBusinessForOperation(token,{mode,atHead,workspaceId})` returns an at-most-1MiB clone with exact business/decision/publication/receipt/audit refs and one status for each source occurrence. `new` requires a current exact head and human/current source use. `historical` requires an exact currently reachable head and current registered reader; loss of source use or local bytes is an explicit blocker, while loss of reader/key/workspace or unsafe path refuses the lookup. Null business refuses in both modes. Previous business revisions are semantically checked, but inactive predecessor source bytes are not opened or claimed currently available.

The query's closed data descriptors, nested head and existing contract UUID are checked before the native callback. The initially observed current head is checked after each native callback, before every selected source open, and at return. Historical selection may use an ancestor, but the current head observed at entry must stay stable during selection. A post-commit error discloses the exact owned receipt only after the original principal, role, retained key, read/publish/source grants and canonical packet ownership have been checked again. Another registered human cannot receive that receipt.

Every selected source occurrence is checked against current **business** source ID grant before open, even repeated IDs or identical refs. Local safe regular single-link file reads use Store path checks and hash; Drive is unavailable without fallback. Per-file 1MiB and selected total 16MiB are counted per occurrence, with no deduplication. A 16-ref repeated 1MiB file is the feasible aggregate boundary; 17 refs are schema-invalid, and 16 allowed refs cannot exceed 16MiB unless an earlier per-file guard fires. Unsafe path/root/type is a whole refusal. Store 1MiB/file, 32MiB closure, 4096 files, 128 heads, 64 writes and 512 external refs remain unchanged.

`configureBusinessGrant` is trusted quiescent filesystem-owner configuration only. The separate private file is outside the domain root; a new file requires expected SHA null, and an update requires exact old hash, verified byte-preserving backup, retained key, atomic replacement and readback. The future Kernel connection must separately enforce exclusion from the operational root. Private keys, policy and source bytes are absent from the public result and Store closure.

An older binary cannot interpret the new business-decision kind and must be fenced from new heads. There is no automatic migration, prior-context re-signing, backup promotion, operation selection authority, import/region/lineage proof, commissioning, request/start or actual native integration here. Contract validity, operational compatibility, visual testing and human approval remain distinct. All inherited gates and deferred user testing remain.

BA1-R1 authored qualification uses disposable isolated roots, signed semantic faults and receipt/head rehash faults. Store-level invalidity is reported as the first guard where a coherent receipt or SKU index cannot be constructed. The old-reader fence is a static compatibility requirement; this local focused allocation does not execute an old binary against a new head. Product and template publications use their existing governed writers in the same disposable Store. No runtime integration or external event delivery is inferred from these fixtures.
