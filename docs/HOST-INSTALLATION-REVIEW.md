# Operational installation change: implementation and limits

This is a user-directed requirement change dated 17 October 2026. Earlier source did not promise or implement verified role-session installation. The new lifecycle is implemented around existing function contracts; operational installation of the preserved Windows workspace remains **incomplete** in this cloud environment. See candidate.json and evidence/checks.json for exact source identities.

## Implemented

Installation owns capability discovery, role instruction provisioning, stable host creation keys, distinct session identities and project-scoped bearer bindings, fresh read proofs, Conductor-originated readiness routes, recipient receipts, replacement and initial handoff verification. It creates a private backup before host changes and excludes concurrent installers. The actual host supplies session creation/resume and applicable native image/byte evidence through a small private driver; no fabricated native provider ships.

Bindings, routes and receipts share existing SQLite transactions/backup; no schema migration or architectural reset. Revocation blocks old session bearers. Generator cannot allocate/start an iteration absent its actual Conductor dispatch route. Assigned-executor intake remains independent and assignment-bound. Scoped Kernel command transport supports hosts whose shared files work but cross-execution loopback does not; recover:false leaves active invocation state and owner responsibility intact.

Conductor does creative commissioning/interpretation and delegates operations; Generator and Butler have reusable role helpers. The Butler session does not replace the independent deterministic timer/startup/validation. Image setup calls, automatic uncertain retries, paid providers and design acceptance are absent.
