# Deterministic PNG service (J08)
This bounded local implementation consumes authenticated, frozen J07 operation selections. It adds no AI session and no provider. The existing SOL Conductor commissions 1–6 jobs after the existing Butler is ready, then calls `service.assign` with projectId, roundId and jobId. The local trusted owner dispatches them through `runDeterministicServices(kernel, ownerCredentials, {projectId, jobIds})` in host-runtime.mjs. It accepts no recipe, executable, output bytes or arbitrary arguments. No automatic dispatch occurs on discovery, preparation, server startup or read. J09 supplies the full launcher separately.

Use `inspectPillow(absolutePythonExecutable)` only in permitted development/owner tooling to inspect a conventional installation. Review and supply the complete returned configuration as Kernel/serve `services`, alongside explicit products/templates/imports and `operations:true`. Configuration pins Python executable bytes/version, Pillow core and Image module hashes/version, zlib version and the packaged fixed worker hash. It is local owner configuration; templates cannot set it. Dispatch rechecks the pins and actual versions. The tested version tuple and measured hashes belong in the private return evidence, not a portable claim about every host.

## Structured recipe
The adopted operation declares verified-image input roles `scene` and optional `logo`, PNG output roles, and bounded typed exploration parameters. Every selected source has an exact product/artifact/version/hash/dimensions reference and zero regions; attachments are not executable inputs. A service-produced composite cannot be used as scene: choose its retained uncomposited parent explicitly.

Within the unchanged 24-parameter dictionary, select `recipeversion:1`, shared integer `cropx,cropy,cropwidth,cropheight`, and `out0width,out0height` through the requested output count (max six). With logo select `logowidth,logoopacity,logomarginx,logomarginy,logoanchor` (top-left/right or bottom-left/right). Per-output `outNcropx/cropy/cropwidth/cropheight` and `outNlogowidth/logoopacity/logoanchor/logomarginx/logomarginy/logox/logoy` may override shared values when declared by the adopted template and within the same parameter ceiling. Six outputs with shared crop/logo use 22 parameters. Two channels can use different crop overrides within that ceiling. Extra fields reject; selected template instructions grant no executable, filesystem, provider or retry authority.

Coordinates are integer decoded-original pixels. Cropping precedes aspect-preserving LANCZOS contain resize onto explicit opaque white RGBA canvas, then the selected logo is resized at preserved aspect ratio, its alpha multiplied by opacity and composited at explicit pixel coordinates. Exact resulting layer dimensions and four edge spacings are frozen in each recipe. Output is 8-bit non-interlaced RGBA PNG, compression 9, optimize false, stripped metadata. No implicit generative call, creative treatment search or posting occurs. A channel crop correction is another explicitly commissioned deterministic job referencing the same immutable scene and chosen logo; successful siblings remain intact. The full recipe hash and original scene/logo references accompany produced artifacts and standard execution-result receipts. Human design acceptance remains separate.

## Invocation and recovery
The fixed Python worker receives no template command arguments: only `-I -B <reviewed packaged worker>`, a private assigned cwd, fixed filenames and validated JSON. Parent/child independently check input hashes, PNG policy and dimensions; child decodes the exact hashed in-memory bytes. RootGuard rejects path/link escapes. Ordinary input/output remain <=16MP/24MiB; experimental 20MP capability grants no J08 allowance.

Dispatch is serial with a root-wide durable unresolved-process gate. The existing job allocation/attempt ID, reserved single allowance and once-only start precede spawning. Every duplicate start rejects. Duplicate dispatch skips started/resolved jobs; concurrent dispatch cannot win another start. A definite pre-start failure records a blocked service report with no invocation and allows another explicit dispatch after the cause is fixed, validating retained staging bytes exactly. Any error after durable start, including timeout before apparent output or lost acknowledgement after output, stays uncertain and cannot authorize another invocation. Owner restart retains the original assignment. `reconcileDeterministicService(kernel, ownerCredentials, {projectId,jobId})` verifies original output/receipt for that attempt and replays standard delivery/intake/report; it never invokes the editor.

A fixed configured adapter is not a claim of tool readiness; actual pin/probe/output checks establish compatibility on the current host. The process has a bounded 1–120000ms budget and 1–128KiB log limit per stream, is killed on timeout/overflow and records closed/exit/signal/timing/stdout/stderr. Default budget is 30s/64KiB. Fixed output filenames are exclusive; PNG/receipt publish via partial files and rename. Intake independently validates bytes and frozen output dimensions/limits. A nonzero child exit records failure with exact private diagnostics. A timeout/error records uncertainty. Service actor reports carry null tier and the allowlisted service ID, never a fake LUNA worker. Butler still presents/account-checks the whole batch and creates the existing checkpoint/event; blocked/uncertain jobs prevent completed status. Delivery success cannot establish human acceptance.

## Root compatibility and private recovery
Service-enabled roots use marker v5 with deterministic-service.v1 and SQLite user_version 3; older source refuses them. An existing v4 root requires a matching verified combined backup, unchanged DB/domain head/marker and explicit confirmed quiescence before promotion. This code path is tested only on disposable authored roots; no real migration is authorized. Schema and marker promotion remain separate fail-closed writes: an interruption between them refuses opening instead of guessing recovery. Roll back only through the preserved pre-promotion combined backup into new separate roots with matching source/configuration, preserving all later work; never edit a marker or downgrade a live database.

Combined backups verify frozen selection/service/result links and include allowlisted staging/output/receipt/process bytes and original SQLite blobs. Any started process without explicit quiescent evidence prevents service staging backup; unknown running processes are not presumed dead after restart. Late receipt without process closure may register exact validated output while leaving dispatch/backup blocked pending actual quiescence evidence. There is no automatic process-discovery or advanced recovery orchestrator. Preserve diagnostic roots; do not delete uncertain staging or fabricate a second invocation to clear a gate.

All inherited native/setup/recovery/C1/memory/intended-host/IMG20 and real user gates remain open as recorded in supervisor v48. Three structures, file-owned business/product/template authority, SQLite operations and distinct template statuses are preserved. Environment-first/BVE-last; full launcher J09, native creative route J10, calibration J11 and handover J12 remain later jobs. No production installation, real migration, paid/native provider execution, publication, merge or release is implied by authored tests.


## Later closure after recovered output
Output recovery and host process closure are separate facts. Reconciliation replays the original result-report payload exactly, including an original quiescent:false. If genuine closure arrives later, the assignment-scoped service.quiescence operation reads the fixed private process.json and frozen command, checks its exact hash, process/timing fields and attempt binding, then appends one serviceClosure witness and a quiescent event. It changes current processQuiescent authority without rewriting the result report, artifact, execution-result timestamp/provenance or any earlier receipt. The normal receipt payload-conflict rule remains strict. Verified closure is monotonic; replaying an older uncertain report cannot reopen a closed process.

New host process receipts carry assignmentId and attemptId. Existing receipts retain their exact bytes and are supported through their original private assigned location paired with the exact frozen command; no global PID lookup or presumed process death is used. The physical local owner remains the trusted source of OS close-event evidence. A missing process.json or closed:false supplies no closure authority. This is not a signed OS attestation or process-discovery platform.

Combined backup/restore verifies the new witness against its separate receipt/event and exact staged process/command bytes. One closure witness is permitted per assignment. Missing, changed, foreign-attempt or malformed closure evidence refuses clearing the gate; missing or changed witnessed staging also refuses backup. The existing v5/SQLite3 service format remains; only bounded records/receipts in the existing tables are added. No real root migration is performed. All earlier gates and restrictions remain.
