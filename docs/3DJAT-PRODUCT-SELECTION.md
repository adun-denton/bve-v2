# Trusted base-product selection (PD1 candidate)

`DomainProducts.resolveBaseProductForOperation(token,{mode,atHead,productId})` is an additive file-owned read. It requires a configured native `authenticate` callback and a matching current private product principal. It never falls back to a private bearer after a missing or invalid native identity. The existing command, review and standalone dossier readers retain their existing behavior.

The closed selector input and nested head reference are checked as portable own data before any native callback. The product ID is validated with the existing product UUID command contract at that boundary. Invalid fields return their specific validation codes; a valid but unknown UUID follows the ordinary missing-product path.

`mode:'new'` requires a human callback and the current exact head. `mode:'historical'` requires a selected head reachable in the current head closure and current product read scope. The private policy is reopened after each native callback and at return; the same caller, retained verification key and current head are required. This is an offline interface contract; the actual host's native session binding is not qualified by authored callback tests.

The selected head's product publications are folded in order. The read reconstructs signed create, note, base proposal, decision and correction packets and checks their exact immutable evidence, MAC, role, Store receipt record order/cardinality, product changes/transitions and canonical payload hash. Pending, rejected or superseded claims do not install facts. An accepted proposal can install base `material`, `dimensions`, `sellingPrice`, `workingName` or `productCode`; signed evolution retains the source references of the currently installed metadata fields even though the product record stores plain strings. Notes are historical text. Dossier fields and typed entries remain separate.

Every signed base event's `recordedAt` must satisfy the existing canonical UTC timestamp contract, including create without a note and proposal submission. The semantic receipt audit reconstructs the expected event after this check. Authored validation covers malformed but correctly signed times; it does not replace independent host/session qualification.

The result is a bounded clone of exactly `{head,productId,principalId,product:{reference,record,acceptedFacts},sourceStatus:{base:[{source,status,cause}]}}`, with acceptedFacts equal to the selected product facts. Base source entries follow material, dimensions, sellingPrice, workingName, productCode order and preserve repeats. New mode requires current source grants and safe local source bytes/hash; historical mode can return explicit unresolved source-use or availability blockers after read/product authorization. Revoked source IDs are never opened. Source byte budget is 1 MiB each and 16 MiB aggregate; output JSON is at most 1 MiB. The current Store's 1 MiB/file and 32 MiB closure limits remain unchanged.

This base-only method refuses `CAPABILITY_UNAVAILABLE` if selected-head publications involve the selected product's dossier or attachment, or if selected product attachment/typed arrays are nonempty. Empty schema arrays are valid. A later dossier or attachment publication does not by itself invalidate a reachable earlier base-only historical head. Business context, dossier materialization, attachment configuration/bytes, imported assets and SQLite lineage are outside the result. It is not whole-operation authority and cannot commission or start work. No new host route or runtime wiring is installed.

## Full product composition (PD2 candidate)

`DomainProducts.resolveProductForOperation(token,{mode,atHead,productId})` extends the same strict selected-head fold to all seven mutating product commands. It retains the base selector's native/current private authorization and closed query, exact current human head for `new`, currently reachable selected head for `historical`, and entry/return identity, key, policy and head checks. It does not change the base-only API or legacy command/review/dossier readers.

The result is a cloned ordinary-data object with exactly `{head,productId,principalId,product:{reference,record,acceptedFacts},dossier,attachments,sourceStatus}`. `dossier` contains **every** accepted materialized record at the selected head in publication order as `{reference,record,active}`. The active marker is derived from the latest accepted record for its field or logical entry; inactive records retain their historical body, previous/proposal/decision refs. A scalar's accepted value resides in its dossier record, including an accepted unknown/null value. Typed product entries carry exact dossier-record and attachment references. Pending and rejected text and free notes remain separate. `attachments` contains every selected product member as `{reference,record,current:{status,cause}}`, with current status from mapped, currently permitted captured bytes. `sourceStatus` has `base`, `dossier` and `attachments` arrays, preserving each source occurrence and its explicit verified/unresolved cause. It contains no private source root, bytes, key or token and grants no operation readiness.

New mode requires current use of installed base and **active** dossier sources and all selected captured attachments. A missing, revoked or unavailable source belonging only to an **inactive** accepted dossier record stays in the result as an unresolved historical blocker without alone preventing an otherwise valid new read. Current product/read authority loss refuses both modes. Historical mode can expose explicit source blockers under current read authority and never opens revoked or unmapped bytes. Unsafe path/root/closure/evidence failures refuse either mode. The attachment check uses the existing `AttachmentFiles.authorize` and streamed `verify` on the captured destination. It does not require the external original file or its input directory to remain, and never recaptures or cleans files. The normalized current source map/product permission is rechecked at return; an in-call root remap invalidates the measurement. No historical external root identity is inferred.

The signed fold reconstructs exact complete event/MAC, evidence reference, packet/role, previous product CAS, writer record order, Store-appended product, transitions and canonical receipt payload hash for create/note/base proposal/decision, attachment register, dossier proposal/decision. Accepted dossier decision receipts have `[evidence,dossier-record,dossier-decision,product]`; dossier supersession does not copy a correction proposal, while a base supersession can. Full dossier records do not inherit the proposed snapshot body's 24-item limit. Local metadata sources share one 1 MiB per occurrence/16 MiB aggregate budget across base and dossier. Selected attachment declared bytes count once per member in append order, including unavailable or corrupt members; exceeding the existing 1 GiB review limit refuses before another captured-byte open in both modes. The existing per-file 256 MiB and 1 MiB streaming buffer remain in force. The complete canonical UTF-8 result, wrappers and duplicated facts included, refuses above 1 MiB without truncation.

This is product file authority only. Business signed authority, imported original/region/parent proof, SQLite frozen selection and request/commission/start fences, real native host binding, recovery, memory/responsiveness, browser/intended machine, Windows/platform links and IMG20 remain separate OPEN gates. User testing is deferred pending development and integrated independent review. No merge, release or production installation follows this candidate.

The focused PD1-R2 authored suite observes the actual reader's Store source opens, return-boundary identity/policy/head changes, signed historical decision/correction faults, and a result-size boundary under the unchanged Store and response limits. Its synthetic accepted Drive publication is labeled as an authored historical fault fixture: the ordinary writer rejects remote-source acceptance. It qualifies the strict reader's unavailable-source branch only, without claiming Drive fetching or writer support. All fixtures are offline evidence; independent source review, native host qualification and operational integration remain separate.

The focused PD2 qualification uses genuine product, dossier and attachment writer positives before signed synthetic semantic faults. It distinguishes the exact accepted four-member and nonaccepted two-member dossier decision plans, attachment entity CAS zero from the product's nonzero revision, and selected-product pointer preservation across an unrelated product publication. Portable wrong-type source paths are unsafe whole-lookup refusals even for inactive historical dossier material; ordinary missing or corrupt inactive sources remain explicit blockers. A source reader can select historical content under current scope, while new mode remains human-only. These authored file fixtures do not exercise Windows attachment capture/link behavior, native session binding or business/operation readiness. Passing authored checks do not accept the PD2 candidate; independent supervisor review remains required.
