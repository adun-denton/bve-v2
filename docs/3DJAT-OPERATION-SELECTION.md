# J07-C2-P0 operation selection inspection

This source-only slice defines an immutable `operationSelection` document without installing a writer, reader, route, schema migration or authority resolver. The file-owned business, product, template and signed history remains distinct from operational SQLite snapshots. The selected operation and optional Brand retain their exact historical revisions and per-applicability decision references even after newer drafts. Product base facts remain separate from governed dossier extension records. Templates, instructions and historical permission evidence grant no tools, sources, staff, budgets or permissions.

`{id,schemaVersion:'3djat.operation-selection.v1',body,bodySha256}` has closed fields. `body` has exactly `workspaceId,projectId,requestId,principalId,sessionId,createdAt,domainHead,product,dossier,business,operation,brand,closure,run,permissionEvidence`; `run` is the unchanged `3djat.operation-run.v1`. `row.id=run.runId`. `bodySha256` is lowercase SHA-256 of UTF-8 sorted-key JSON of `body` followed by LF. The proposed SQLite `doc` would separately be sorted-key JSON of the entire row plus LF, with a 48 MiB ceiling. This file does not write it. The 1 MiB file, 32 MiB closure and 4096-file limits are imported from `STORE_LIMITS`; overflow refuses. Arrays retain declared order. Closure paths and dossier paths, permission template/source ID sets are strictly ascending and unique. Original source/region and parent identities are frozen.

The pure closure reader is `Object.create(DomainStore.prototype)` with a supplied byte-map `readFile`, matching the existing `verifySelection` strategy. It creates no `DomainStore`, DB, Kernel, root, timer, process, provider or native session. It validates the actual source closure rules and binds embedded records to that closure. A signed template action's MAC and current active choice require private retained key history and native caller scope. Structural publication/receipt linkage alone is never an authority result. A caller's `authenticated`, `macVerified`, `retainedKey`, `sourcesAvailable` or access-file pathname cannot turn the verdict into `selectable`, `ready` or `permission-granted`. Four independent contract validity, operational compatibility, visual testing and human approval statuses remain separate.

The snapshot's historical decision may differ from the latest template indexed by the frozen head. This module mirrors `validateResolvedOperation` relations while replacing only its two latest template membership predicates with a structural exact historical decision link. It never calls that legacy helper with a fabricated head and does not catch away general `HASH_MISMATCH`. A trusted future resolver must replay full signed publication history, prove exact active per-applicability membership at the frozen head, MAC and current native/private source grants, and repeat those checks before preparation and attempts. Historical receipt lookup is separately scoped to a currently authenticated principal; it is not a new request, commission or attempt start. Source unavailability can block future work without rewriting frozen evidence. No prior backup is demanded merely to create a request; combined backup/recovery is a later gate.

The proposed format predicate is limited to `[operation-selection.v1]`, `[historical-import.v1,operation-selection.v1]`, and `[historical-import.v1,png20-experiment.v1,operation-selection.v1]`. It installs no global operational-kind allowlist. A literal-producer-only list of 30 is incomplete: `src/asset-import.mjs`'s generic `immutable(db,kind,...)` also produces `importDeclaration`, `importReceipt`, `importArtifact` and `importOrigin`. Any future global allowlist needs an independent full producer audit, conditional import/IMG20 rules and compatibility review. Ordinary 16 MP/24 MiB and experimental-only 20 MP policies do not change here.

The test fixture is a complete authored in-memory marker, workspace, genesis, head and receipt chain, with immutable product, operation and Brand decision records, later unadopted drafts, and an optional second product revision with a published attachment. Each invocation allocates independent objects and contexts. The attachment check requires the exact ID/revision/path/hash, attachment kind and identity, selected product ownership, and membership in the frozen product's attachment references. It does not read attached source bytes or prove a current grant. Invalid base64, encoded length overflow and decoded/aggregate capacity are distinct refusals; small authored tests cannot qualify the largest bounds or OS memory behavior. These tests establish only the pure module behavior. They do not establish source access, native authentication, signed MAC history, SQLite integration, backup/restore, performance, OS/platform or user acceptance. C1 lock/publication observations and all inherited gates remain open.

## Template-side trusted selector (J07-C2-P1-T1)

`DomainTemplates.resolveAdoptedForOperation(token,{mode,atHead,projectId,applicability,operationTemplateId,branded,brandTemplateId})` is an additive local method. The query has exactly those seven fields; `mode` is `new` or `historical`, and unbranded calls require a null Brand ID. It requires the class's native `authenticate` callback, current matching private principal and template read grant, product scope, and a retained private verification key. A standalone bearer or access-file pathname does not qualify. The method folds the complete published signed history through the existing `history/auditOf` logic. It selects the active decision at the specified applicability, including an earlier adopted revision after a later unadopted draft, and handles an explicit separate Brand ID. An unsupported decision stream or unavailable retained key fails closed. The current code supports no withdrawal command or key rotation history.

`new` requires the selected head to be current before and after the call and a native human identity. It requires current source-use grants and verified selected local file bytes. `historical` requires the exact old head in the **current reachable chain**; it grants only a currently authenticated scoped read. A missing source-use grant, missing/changed local source or unsupported Drive source appears as a blocker without erasing readable signed provenance. It does not read bytes for a source ID outside the current grant. Missing product/template/applicability read scope refuses the historical call. A product UUID must exist at the selected head; this proves existence, not product history. The method rechecks the current head, same native ID/role, current private grants and exact retained key after source reads.

The bounded cloned result has exactly `{head,productId,applicability,operation,brand,principalId,sourceStatus}`. `operation` and non-null `brand` each have `{reference,record,decisionReference,decision,publication,receipt}`. `sourceStatus` is `{operation:[{source,status,cause}],brand:null|[{source,status,cause}]}`, where each `source` is the exact selected source reference, `status` is `verified` or `unresolved`, and `cause` is null or the actual blocker code. One shared reader limits selected file sources across operation and Brand to 1 MiB each and 16 MiB total. The entire returned JSON is at most 1 MiB. No key, token or source byte is returned. This serialized result is ordinary data, never an unforgeable capability or a whole operation authorization. Product/dossier/attachment provenance, P0 row and database inventory, current operation compatibility, visual testing, human approval, request/commission/start and native execution remain separate tasks.
